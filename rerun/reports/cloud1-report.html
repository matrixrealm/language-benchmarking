2. What the data supports

A not supportedThe GIL caps CPU-bound Python; the free-threaded build lifts the cap

On /pycpu the GIL build, the free-threaded build and the forced-GIL control all passed at 10 to 30 RPS and all collapsed at 40 RPS. At 30 RPS the GIL build had the lower p99 (31 ms against 46 ms) and used less CPU per request. The GIL cap is visible in CPU use: the GIL builds never exceed 1.0 core, while the free-threaded build does spread across cores (about 1.27 at 30 RPS and 2.0 at 40 RPS). But it turned the extra cores into higher CPU cost per request, not into higher throughput: its ceiling was the same as the GIL build's, and at 40 RPS it did worse (0 successes against a handful).

B supportedForced-GIL control

The free-threaded build with the GIL forced back on (-t-gilon) matches the free-threaded build on memory and CPU cost, and matches the GIL build on latency. The extra memory and CPU belong to the build, not to the GIL setting.

C supportedWaiting calls: virtual threads and Go versus a 200-thread pool

Go and Java virtual threads passed /park at 250 and 1000 RPS in every repeat. The 200-thread Java pool failed every request at both rates, in every repeat.

D supportedMemory cost at 1000 RPS on /partner

Go 23 MiB, python (aiohttp) 36 MiB, fastapi 55 MiB, Java 217 MiB, all passing the SLO in every repeat. Java is about 9 times Go. The earlier plan figure of about 195 MiB for Java is out of date.

7. The 40 RPS collapse

At 40 RPS every runtime failed all three repeats. The 5-second client timeout is what p99 shows, so this is not a latency measurement. The GIL builds ran at the 1.0-core GIL cap and the free-threaded build at the full 2.0 cores. None was OOM-killed, and the cgroup throttled none by more than half a second. The GIL builds completed a handful of requests (2 to 57); the free-threaded build completed none.

Interpretation, not directly measured: the server cannot clear 40 RPS, so requests queue past the client timeout while the server keeps working on abandoned ones, which drives useful throughput to zero. The candidate log is empty, so this cannot be confirmed from the log. At 30 RPS all runtimes passed, so the usable ceiling lies between 30 and 40 RPS for every build tested (for the GIL builds that is the 1-core limit, since 0.86 cores were in use at 30 RPS). A 35 RPS cell would narrow it.

8. Method and limits

RunnerGitHub-hosted ubuntu-24.04, 4 vCPU (AMD EPYC 7763), 16 GB, Docker 28.0.4, cgroup v2
CPU pinningCandidate on CPUs 0,1 (2 CPUs, 512 MiB, no swap); mock partner, k6 and the sampler on CPUs 2,3
PythonCPython 3.14.3 (GIL build) and 3.14.3t (free-threaded), same asyncio stack for both
Timings--fast: 2 min warmup, 3 min measured, 60 s recovery; 3 repeats per cell, tag cloud1
Loadk6 1.3.0, constant arrival rate (open model)
SLOp99 250 ms (park 1250 ms), failure rate at most 0.1%, no dropped iterations
Noise floorRun #1 (5 repeats each, go partner 250 and aiohttp-nogil pycpu 10): memory 0.9%, CPU 3.2%, p99 0.5% min-max range. That artifact was not re-fetched for this report.
LimitsOne runner per batch, so cross-batch comparisons carry VM-to-VM noise. The leak screen reports insufficient_window on the short runs. CPU ms per request is blank-equivalent when a run has almost no successes.
